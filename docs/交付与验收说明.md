### 知识缺口的判定口径（AC-11 说明）

实现遵循决策 D2 的三条件，并对两处落地细节做了明确：

1. **「有有权上下文」的定义**：低于 `RAG_MIN_RELEVANCE`（默认 0.15）的重排结果不计为有效上下文。
   实测分数分布：强相关 **0.67**、弱相关 **0.03**、不相关 **0.0001**，阈值区分度良好。
   *不加这个下限时，向量检索总有 Top-K 返回，缺口将永远无法识别。*
2. **「非权限拒绝」的定义**：仅当被拦截文档占召回**主体**（`GAP_DENIED_RATIO`，默认 0.5）时
   才判为权限受限；召回里只混进个别无权文档、而用户真正想问的内容本就缺失时，仍记为缺口。
   *不加这个口径时，只要库中存在任何无权文档，缺口识别就会永久失效。*

**仍未覆盖的情形**：与知识库「沾边但不覆盖」的问题（例如知识库只有《售后政策》、用户问
「海外直邮清关延误」，两者同属客服域但文档未涉及该问题）可能因重排分数高于下限而不被判为缺口。
彻底的解法是引入「答案级」判断（由大模型判定资料能否回答问题），成本较高，当前未实现。
两个阈值均可在 `.env` 调整，牺牲精确度即可换取更高的召回。

## 五、生产部署检查清单

| 项 | 动作 |
|----|------|
| 密钥 | 替换 `JWT_SECRET`（当前为开发值）；确认 `.env` 未入库（已在 `.gitignore`） |
| 账号 | 修改初始管理员口令；为应用创建独立数据库账号（`scripts/init_mysql.sql` 可创建 `kb`），**不要直连 root** |
| CORS | 把 `CORS_ORIGINS` 收敛为实际访问域名，移除 localhost 白名单 |
| 静态产物 | 部署前执行 `npm run build`（`dist` 不入库，由后端托管） |
| 进程 | 用 `uvicorn` 多 worker 或 systemd/服务托管启动；健康探针接 `/healthz/ready` |
| 备份 | MySQL（平台数据）、MongoDB（会话）、Milvus（向量）、MinIO/本地目录（原文件） |
| 模型 | 生产建议将嵌入与重排切到 GPU（需先装 CUDA 版 PyTorch）；云模型密钥按最小权限发放 |
| 日志 | 确认日志目录可写；按合规要求设定留存期 |
| 演示 | 准备演示账号与知识素材（可参考 `demo_end_to_end.py` 的两条场景脚本） |

## 六、已知限制

1. **前端无自动化测试**：交互行为需人工确认（清单见 README）。
2. **嵌入与重排运行在 CPU**：宿主机 PyTorch 为 CPU 构建；切换 GPU 需重装 CUDA 版 torch。
3. **单机架构**：导入与查询共享一份模型实例，并发导入会排队（SPEC ADR-007 已记录演进路径）。
4. **知识缺口对"沾边但不覆盖"问题不敏感**：见第二节说明。
5. **PRD/SPEC 中标注 `[待确认]` 的业务口径**（提示文案、FAQ 默认权限语义、切片调整粒度等）仍按当前默认实现，需业务方最终确认。
